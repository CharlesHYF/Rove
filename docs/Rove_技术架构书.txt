01 架构目标与约束
Rove 的架构目标不是把 Crawler、Browser、Elasticsearch 和 Reranker 简单拼接，而是建立一条共享统一数据模型、错误语义和可观察性的 Web → Evidence Pipeline。上层 Agent 不需要知道页面是通过 HTTP 还是 Browser 获取，也不需要直接理解 Elasticsearch 查询细节。
约束
架构响应
必须自有搜索链路
Crawler、Indexer、Retriever、Ranker 均在 Rove Core
动态网页不可忽略
Browser Runtime 为正式一等子系统
Browser 成本高
HTTP First + Browser Escalation + Session Pool
需要传统与语义召回
Elasticsearch BM25 + dense_vector + Hybrid Fusion
Agent 需要证据而非网页
以 Chunk/Evidence 为检索输出单元
Infra 必须可调试
全链路 Trace + TUI Inspector

Scheduler
Scheduler 不做简单 FIFO。选择 URL 时综合 priority、next_fetch_at、host concurrency、robots、crawl delay、retry/backoff 与 freshness。单 Host 必须有独立 token bucket / semaphore，防止某站点占满全局 workers。
URL Canonicalization
规范 scheme/host 大小写、default port、fragment、trailing slash。
去除已知 tracking params，但保留可能影响内容的 query 参数。
读取 rel=canonical 后进行二次 canonical 归并。
Redirect destination 更新最终 canonical_url，不丢失 source relationship。

Dedup
Dedup 分四层：URL dedup → canonical dedup → exact content hash → near duplicate。Near duplicate 可使用 SimHash/MinHash 等 deterministic 方法；不得依赖 LLM。
Chunking
Chunk 以语义结构优先，而不是固定字符切片。优先保持 Heading/Paragraph/List/Table 单元，在超过上限时再进行窗口切分。Chunk 必须保存 heading_path 与 position，便于 Evidence 回溯。

BM25
适合专有名词、错误信息、API 名称、代码符号、Exact Term。Search Fields 采用不同 boost，例如 title > heading_path > chunk.content；具体权重必须通过 benchmark 调整，而不是写死为产品语义。
Vector
Vector Retriever 通过 Embedder 接口获得 query embedding；Core 不绑定供应商。允许 local model、OpenAI-compatible endpoint 或 custom implementation。Elasticsearch dense_vector 负责 ANN/KNN 召回。
Fusion
默认采用 RRF 合并 Lexical 与 Vector Top-K。Fusion 层保持独立，使后续可以引入 weighted fusion 或 learned fusion，而不改变 Retriever 接口。

关键 Architecture Decisions
ADR
决策
原因
ADR-001
Go Core
并发、单二进制、长期 Runtime、CLI/TUI 生态
ADR-002
Elasticsearch 为主 Index
同时满足 BM25、Vector、Metadata Filter 与成熟运维能力
ADR-003
HTTP First / Browser Escalation
控制浏览器资源成本并覆盖动态 Web
ADR-004
Document/Chunk 双层索引
页面级 metadata 与检索单元职责分离
ADR-005
Deterministic First
核心 Infra 无 LLM 依赖仍能工作
ADR-006
Core 与 Interface 分离
TUI/CLI/MCP 共用同一 Runtime，不污染 Domain
ADR-007
Evidence 为最终检索对象
面向 Agent，而不是传统 SERP 用户
架构结论
Rove 的系统边界固定为：Acquire → Access → Understand → Index → Retrieve → Rank → Evidence。Browser Use、Exa、Tavily、AnySearch 等产品只能作为某些设计思想的参考，Rove Core 自己拥有整条基础设施链路。

ADR | 决策 | 原因
ADR-001 | Go Core | 并发、单二进制、长期 Runtime、CLI/TUI 生态
ADR-002 | Elasticsearch 为主 Index | 同时满足 BM25、Vector、Metadata Filter 与成熟运维能力
ADR-003 | HTTP First / Browser Escalation | 控制浏览器资源成本并覆盖动态 Web
ADR-004 | Document/Chunk 双层索引 | 页面级 metadata 与检索单元职责分离
ADR-005 | Deterministic First | 核心 Infra 无 LLM 依赖仍能工作
ADR-006 | Core 与 Interface 分离 | TUI/CLI/MCP 共用同一 Runtime，不污染 Domain
ADR-007 | Evidence 为最终检索对象 | 面向 Agent，而不是传统 SERP 用户
架构结论 Rove 的系统边界固定为：Acquire → Access → Understand → Index → Retrieve → Rank → Evidence。Browser Use、Exa、Tavily、AnySearch 等产品只能作为某些设计思想的参考，Rove Core 自己拥有整条基础设施链路。
